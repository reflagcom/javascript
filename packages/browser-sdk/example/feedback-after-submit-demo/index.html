Does onAfterSubmit survive the user closing the tab?

onAfterSubmit only fires once the feedback POST to Reflag resolves, which means there is a real gap between the user clicking Send/a score and the callback actually running. This page makes that gap visible, and then proves what happens if the tab goes away before it closes.

1. Artificial network latency

Widens the gap between submit and onAfterSubmit so it's easy to watch. The mock API server delays its response by this many milliseconds.

2. Live widget

Open the real feedback widget (built from this branch's src/, not a mock) and submit a score/comment. Watch the banner and log below.

3. Prove it: navigate away mid-submit

This calls the exact same feedback() request the widget's Send button triggers, then navigates away a moment later — simulating the user closing the tab (or clicking a link) right after submitting, before the response comes back. "Server actually received it?" is ground truth from the mock API's own log, independent of anything the browser tab believes happened.

On localhost, the request body is tiny and the round-trip to the mock server is near-instant, so it often finishes sending before the navigation can interrupt it — the row below may well show the server received it either way. On a real network, with real latency, that's not guaranteed: without `keepalive`, closing the tab can lose the request outright. What is guaranteed, every time, is the other column: the client never sees onAfterSubmit fire, because the page that would have run it is gone.

Every row here is a deliberately interrupted attempt — that's the point of this button. "Client saw onAfterSubmit?" reproduces the widget's own await-then-notify sequence; "no" means the page was gone before that sequence could finish.
